# 修复评论与回写

## 评论结构

```text
问题原因
<根因，写具体数据流或判断条件>

修改内容
- <文件或模块>：<改动与目的>

验证
- <命令或操作>：<实际结果>
- 修改前：<证据场景>
- 修改后：<证据场景>

当前状态
代码已提交 <commit>；是否推送、合并、部署按实际情况填写。
```

## 规则

- 原因写根因，不写“已修改”“优化了代码”。
- 验证只写实际执行过的命令和结果；未运行时明确写“未执行”。
- 使用的数据是模拟数据时注明。
- 提交号、分支、部署环境必须与 Git/发布系统一致。
- 涉及界面时同时提供修改前后图；只改一处也必须覆盖工作项指出的位置。
- 评论不得包含 Token、密码、真实身份证明、服务器口令或内部测试账号。

## submit_fix

常用参数：

```json
{
  "work_item": "PROJ-10",
  "reason": "根因",
  "changes": ["文件或模块：改动"],
  "validation": ["验证命令与结果"],
  "commit": "提交号",
  "before_images": ["修改前绝对路径"],
  "after_images": ["修改后绝对路径"]
}
```

先调用不带确认的预览，核对工作项、状态和附件路径，再按用户授权正式提交。工具字段以当前 MCP 返回的 schema 为准。

C/D 类使用 `add_work_item_comment`，正文开头明确“待确认”或“非当前范围”，不设置“已修复”。
